Every job that completes in the v3 API returns an `outputs[]` array. Each item carries an `asset_id` you can pass straight into a later submit's media inputs, so you can chain generations — for example, generate an image, then animate it into a video — without downloading and re-uploading the file in between.

## Reference an output in the next submit

1. Submit the first job and poll `GET /v3/jobs/{job_id}` until its `status` is `COMPLETED`. `outputs[]` is empty until then.
2. Read `outputs[0].asset_id` (or whichever output you want to chain from) — it looks like `asset_<uuid>`.
3. Pass it in the next submit as an asset reference. This excerpt shows the media field; the full Veo 3 request below includes its other required inputs:

```json
{
  "input": {
    "start_image": { "source": "asset", "asset_id": "asset_..." },
    "prompt": "a fixed camera observes a conveyor moving boxes"
  }
}
```

`asset_id` is the only supported way to name a previous job's output. If you pass a `job_<uuid>` in an asset field the API returns a `400` pointing you back at `outputs[].asset_id`.

<Note>
  Earlier drafts of the API described a workaround where you replaced the `job_` prefix of a job id with `asset_` to obtain the asset id. That derivation is no longer supported — read `outputs[].asset_id` instead.
</Note>

## Example: image, then video

Use the [quickstart](/pages/developer/v3/quickstart) to submit an image job and
wait for `COMPLETED`. Then set `JOB_ID` to the printed job ID before running the block below. This block does not submit
another image job.

```bash
RESULT=$(curl --fail-with-body --silent --show-error \
  "https://api.hedra.com/v3/jobs/$JOB_ID" -H "Authorization: Key $HEDRA_API_KEY")
ASSET_ID=$(printf '%s' "$RESULT" | jq -er \
  'select(.status == "COMPLETED") | .outputs[0] | select(.status == "COMPLETED") | .asset_id // empty')
BODY=$(jq -n --arg asset "$ASSET_ID" '{input: {
  start_image: {source: "asset", asset_id: $asset},
  prompt: "A camera moves slowly around the inspection rig",
  aspect_ratio: "16:9", resolution: "720p", duration_ms: 4000, quality: "fast"
}}')
curl --fail-with-body -X POST https://api.hedra.com/v3/models/veo-3 \
  -H "Authorization: Key $HEDRA_API_KEY" -H "Content-Type: application/json" \
  -d "$BODY"
```

The returned job ID belongs to the video job. Wait for that job to complete
before reading or downloading its outputs. Media field names vary by model;
`start_image` is the field in Veo 3's schema.

## Output status

Each item in `outputs[]` carries a `status`:

| Status | Meaning |
| --- | --- |
| `COMPLETED` | The output produced media. `url` and `asset_id` are populated. |
| `FAILED` | The output failed. `error` describes the failure; `url` and `asset_id` are null. |
| `EXPIRED` | The output is no longer available. `url` and `asset_id` are null. |

```python
import time
import httpx

def wait_for_result(job_id: str, key: str) -> dict:
    headers = {"Authorization": f"Key {key}"}
    deadline = time.monotonic() + 600
    while time.monotonic() < deadline:
        response = httpx.get(f"https://api.hedra.com/v3/jobs/{job_id}", headers=headers, timeout=30)
        response.raise_for_status()
        job = response.json()
        if job["status"] == "FAILED":
            raise RuntimeError(f"Job failed: {job.get('error')}")
        if job["status"] == "COMPLETED":
            return job
        time.sleep(5)
    raise TimeoutError(f"Resume polling {job_id}; do not resubmit.")

# Use the job ID printed by your submit and your server-side API key.
job = wait_for_result(job_id, api_key)
for output in job["outputs"]:
    if output["status"] == "EXPIRED":
        raise RuntimeError("Output expired — media is no longer retrievable.")
    if output["status"] == "FAILED":
        raise RuntimeError(f"Output failed: {output['error']}")
    # COMPLETED — download output["url"] or chain output["asset_id"].
```

## Per-output errors

`error` is now published on every kind of output — image, video, and audio — as an error envelope. It is `null` on a `COMPLETED` output and populated on a `FAILED` output, so you can inspect the failure per-item when a job produces multiple outputs.

## Measured frame rate on video outputs

Video outputs now report the real measured frame rate in `fps`. Older jobs whose output was probed before this change may still return `fps: null` — treat `null` as "unmeasured" rather than "no frame rate".
