A sandbox is a container with GPUs that runs in Hedra's cloud and is paid per GPU-hour from your API wallet. `hedra-cli sandbox` creates and stops sandboxes and opens shells, commands, output streams, file copies and port forwards in them.

Until then, every example below uses `$GPU` and never names a model. `hedra-cli sandbox gpus` lists the models your workspace can run, each with its memory, its price per GPU-hour after your workspace's discount, and whether one is free right now.
</Warning>

## Before you start

- **Install hedra-cli** with `npm install --global @hedra/cli`, or see [SDKs and developer tools](/pages/developer/v3/sdks).

<Warning>
**PLACEHOLDER:** the first hedra-cli version that includes every sandbox command on this page.
</Warning>

- **A funded API wallet.** A sandbox's GPU time is paid from the API wallet; see [Billing](/pages/developer/v3/billing).
- **Sandboxes enabled for your workspace.** Until they are, `create`, `gpus` and `quota` answer that sandboxes are not available.

### Sign in with a key that holds the sandbox scopes

The sandbox commands need these key scopes:

| Scope | What it allows |
| --- | --- |
| `sandboxes:read` | Every stream command, and `ls`, `get`, `gpus`, `quota`, `events`, `saved-logs` and `secrets ls` |
| `sandboxes:write` | `create`, `stop`, `token`, `secrets set`, `secrets rm`, `rotate-signing-key` and `port-forward` |
| `sandboxes:exec` | `exec`, `shell` and `cp` |

So `exec`, `shell` and `cp` need `sandboxes:read` and `sandboxes:exec`, `port-forward` needs `sandboxes:read` and `sandboxes:write`, and `shell --gpu`, which creates, opens and stops a sandbox, needs all three. `secrets set`, `secrets rm` and `rotate-signing-key` also need you to be a workspace owner or admin, or the member who pays for the workspace.

Sign in with:

```bash
hedra-cli auth login
```

The key `auth login` stores holds every scope except `all` and `keys:manage`, so it holds the three sandbox scopes whatever your role in the workspace. Running `auth login` again, or `hedra-cli workspaces select`, renews the key you already hold and resets its scopes to that same set.

A key you mint yourself, on the console's [API keys page](https://www.hedra.com/develop/api-keys) or with `hedra-cli keys create`, holds the sandbox scopes when it lists them or holds `all`. Any workspace member can mint a personal key that lists them. Only a workspace owner or admin, or the member who pays for the workspace, can mint a key that holds `all`, or a service key. A key minted before key scopes existed holds `all`.

A key in `HEDRA_API_KEY` takes precedence over the one `auth login` stored, so CI and agents can use a key of their own:

```bash
export HEDRA_API_KEY="<key_id>:<secret>"
```

`hedra-cli auth status` shows which credential the CLI is using. When a key lacks a scope, the command's error names the missing scope.

## Two kinds of sandbox command

The `sandbox` group has two kinds of command, which take the sandbox in different ways.

**API commands** map one-to-one onto the [v3 sandbox API](https://api.hedra.com/v3/openapi.json) and take the sandbox as `--sandbox`, either its name or its `sandbox_` id:

```bash
hedra-cli sandbox stop --sandbox train
```

**Stream commands** hold a connection open to the sandbox and take it as the first argument:

```bash
hedra-cli sandbox logs train
```

| Command | Kind | What it does |
| --- | --- | --- |
| `gpus` | API | List the GPU models your workspace can run |
| `quota` | API | Show how many more GPUs your workspace's sandboxes can hold |
| `create --name <name> --gpu <model>:<count> --image <ref>` | API | Create a sandbox |
| `ls` | API | List your creating, active and stopping sandboxes; `--all true` adds ended and failed ones |
| `get --sandbox <sandbox>` | API | One sandbox, with its instances and its charge so far |
| `stop --sandbox <sandbox>` | API | Stop a sandbox |
| `token --sandbox <sandbox>` | API | Mint a token for the sandbox's URL |
| `saved-logs --sandbox <sandbox>` | API | The stored copy of an instance's output, as a JSON object |
| `events --sandbox <sandbox>` | API | An instance's events |
| `secrets ls`, `secrets set`, `secrets rm` | API | Manage the workspace's sandbox secrets |
| `rotate-signing-key` | API | Revoke every session and endpoint token of the workspace's sandboxes |
| `exec <sandbox> -- <command>…` | Stream | Run a command and relay its input, output and exit code |
| `shell <sandbox>` | Stream | Open an interactive shell |
| `shell --gpu <model>:<count> --image <ref>` | Stream | Create a sandbox, open a shell in it, and stop it when the shell ends |
| `logs <sandbox>` | Stream | Print the main process's output; `-f` keeps following it |
| `attach <sandbox>` | Stream | The same as `logs -f` |
| `cp <source> <destination>` | Stream | Copy files and directories in or out |
| `port-forward <sandbox> <local>:<remote>` | Stream | Forward a local port to a port in the sandbox |

<Warning>
**PLACEHOLDER:** confirm that sandbox secrets reach a sandbox at launch; if they do not, remove the `secrets` row and `--secrets` below.
</Warning>

A name is 1 to 32 lowercase letters, digits and hyphens, starting and ending with a letter or digit. It is unique among your creating, active and stopping sandboxes, so a name reaches your live sandbox of that name, or else your newest one. A stream command resolves the name once and keeps the id, so a reconnect never reaches a later sandbox that reuses the name.

Run `hedra-cli sandbox <command> --help` for every flag. `--dry-run` checks a command's arguments and sends nothing.

API commands follow hedra-cli's usual output: a table on a terminal and JSON when stdout is piped, with `--format`, `--query` and `--quiet` as for every other command. A stream command's stdout is the sandbox's own output, so it writes its own messages and errors to stderr.

## The quickest start: a shell on a new sandbox

```bash
hedra-cli sandbox gpus
export GPU=<model>:1
hedra-cli sandbox shell --gpu "$GPU" --image pytorch/pytorch:latest
```

`shell --gpu` creates a sandbox named `shell-` and six random characters, waits until it is ready, opens a shell in it, and stops it when you exit the shell. Billing ends at the stop request. While it waits, it prints its progress on stderr, and it warns first when no GPU of that model is free (the sandbox may then wait up to 15 minutes for one) or when your workspace's GPU quota is too small.

- `--max-duration` stops the sandbox this long after it is created, such as `90m`, `8h` or `2d`; the default is `24h`.
- The sandbox also stops on its own about 15 minutes after its last activity, so a sandbox whose CLI crashed or whose laptop went to sleep does not run for the full 24 hours. An open shell counts as activity from its start until it exits. A process left running in the background, such as a `tmux` server or a `nohup` or `&` job, does not.
- It needs a terminal on stdin and stdout, and refuses before it creates anything when it has none.
- If the connection drops, the sandbox keeps running. hedra-cli prints how to reopen the shell with `hedra-cli sandbox shell <name>` and how to stop the sandbox. A reopened shell's exit does not stop the sandbox; its idle limit does, or `stop`.

## Create a sandbox

```bash
hedra-cli sandbox create \
  --name train \
  --gpu "$GPU" \
  --image pytorch/pytorch:latest \
  --command python --command train.py \
  --env '{"EPOCHS": "3"}' \
  --ttl-seconds 28800
```

- `--gpu` is `<model>:<count>`, with a count from 1 to 99 GPUs per instance.
- `--command` replaces the image's entrypoint; pass it once per argument. Without it, the image's `ENTRYPOINT` and `CMD` run. The sandbox ends when its main process exits.
- `--env` takes a JSON object. Answers return only the keys.
- `--ttl-seconds` stops the sandbox that many seconds after it is created, from 120 up to 365 days. Without it, the sandbox runs until you stop it, its command exits, or the wallet cannot pay.
- `--ports '{"port": 8888}'` serves that port at the sandbox's `url`; see [Reach a sandbox's URL](#reach-a-sandboxs-url).

For a sandbox you work in interactively, with no main process, pass `--idle true`. Add `--idle-ttl-seconds` to stop it once it has had no activity for that long. Activity is an `exec` or `shell` session, from its start until its process exits, and a request to its `url`. A `port-forward`, an `attach`, and a process left running after its session ends are not activity.

```bash
hedra-cli sandbox create --name dev --gpu "$GPU" --image pytorch/pytorch:latest \
  --idle true --idle-ttl-seconds 1800
```

The command returns once the sandbox is created. Its instances may still be starting: check with `get`.

## List, inspect and stop

```bash
hedra-cli sandbox ls
hedra-cli sandbox ls --all true
hedra-cli sandbox get --sandbox train
hedra-cli sandbox stop --sandbox train
```

`get` shows each instance's status and, for one that failed, its `failure_reason`, and the sandbox's `end_reason` once it has stopped. `stop` answers with the sandbox in `stopping` and returns; Hedra records it `ended` usually a minute or two later, once every instance has stopped. Billing ends at the stop request.

## Run commands

```bash
hedra-cli sandbox exec train -- nvidia-smi
hedra-cli sandbox exec train --env STEP=2 -- python eval.py
echo hello | hedra-cli sandbox exec train -- cat
hedra-cli sandbox exec train -t -- htop
```

`exec` runs the command after `--` without a shell, relays your stdin to it and its stdout and stderr back, and exits with the command's own exit code. To use shell syntax, run a shell: `-- sh -c 'cd /work && make'`.

- `-t` runs the command on a terminal, with yours in raw mode, for programs such as `htop` or `vim`.
- `-n` sends no input: the command sees the end of its input at once.
- `--env KEY=VALUE` sets a variable for the command; repeat it for more.
- `--term` sets the remote `TERM` under `-t`; by default it is yours, or `xterm-256color` when the image may not know yours.

`shell <sandbox>` opens an interactive shell in a running sandbox: the one the image's `SHELL` variable names, else `bash`, else `sh`. Its exit does not stop the sandbox.

## Read the output

```bash
hedra-cli sandbox logs train
hedra-cli sandbox logs -f train
hedra-cli sandbox attach train
```

`logs` prints the main process's recent output and exits. While the sandbox runs, the output comes live from the sandbox. Once it has stopped, `logs` reads the stored copy, so it is also the command for reading a stopped sandbox's output. The stored copy keeps only the newest part of a long output, and `logs` says when older output was dropped.

`logs -f`, and `attach`, which is the same, keep printing new output until you press Ctrl-C. They wait up to 15 minutes for a sandbox that is still starting, reconnect after a dropped connection, and when the sandbox stops, print the rest from the stored copy and exit.

`logs` and `attach` read the first instance (replica 0).

`saved-logs` is an API command and answers JSON, not the output as text: an object with the output in `content` and `truncated` set when older output was cut. Use it to read another replica's stored output with `--replica`, or output since a time with `--since`:

```bash
hedra-cli sandbox saved-logs --sandbox train --replica 1 --format json | jq -r .content
```

## Copy files

```bash
hedra-cli sandbox cp ./data train:/work/data
hedra-cli sandbox cp train:/work/out ./out
```

One side of `cp` is `<sandbox>:<path>` and the other a local path. It copies a file or a whole directory either way.

- When the destination is an existing directory, the source lands inside it under its own name. Otherwise the source takes the destination's name, and its missing parent directories are created.
- A source ending in `/.` copies the directory's contents rather than the directory.
- A relative sandbox path is relative to the sandbox's working directory.
- The image needs `sh` and `tar`.

`cp` exits with the code of `tar` in the sandbox, which is 0 for a complete copy. A copy that left out or refused an entry, or that lost output, fails with exit code 255 and says what is missing.

## Forward a port

```bash
hedra-cli sandbox port-forward train 8888
hedra-cli sandbox port-forward train 9000:8888
hedra-cli sandbox port-forward train 0:8888
```

`port-forward` listens on your machine's `127.0.0.1` and `[::1]` and forwards each connection to the port in the sandbox until you press Ctrl-C. Give one port for both sides, or `<local>:<remote>`; a local port of `0` picks a free one, which it prints. Up to 90 connections are open at once; one more waits for one to close.

The server in the sandbox must listen on `127.0.0.1` or on every address. One bound only to `::1` or to another address is not reached.

<Warning>
**On a shared machine, anyone logged in to it can use your forwarded port.** The listener accepts connections from any local user, as `ssh -L` and `kubectl port-forward` do, and a forwarded connection skips the endpoint-token check that protects the sandbox's `url`. Forward only on a machine whose other users you trust with the sandbox, and stop the forward when you are done.
</Warning>

A refused or dropped connection resets only that connection, and the forward keeps listening. The forward stops with an error only when no later connection could succeed: the sandbox stopped, or the key lost its scope or was revoked.

## Reach a sandbox's URL

A sandbox created with `--ports` serves that port at its `url`, which needs a token. `token` mints one:

```bash
hedra-cli sandbox token --sandbox train
```

It answers:

- `token`, sent as `Authorization: Bearer <token>` to `url`;
- `url`;
- `browser_url`, a link that opens `url` in a browser and keeps that browser signed in to the sandbox;
- `expires_at`: the end of the sandbox's `--ttl-seconds`, or 30 days after the mint, whichever is earlier.

The token and `browser_url` are credentials: anyone who has either one reaches the sandbox until it expires. `rotate-signing-key` revokes every token and session of your workspace's sandboxes.

## Exit codes

API commands exit with hedra-cli's usual codes: 0 on success, 1 when the API answers with an error (a refused key included), 2 when no credential is found, 3 for a usage error, 4 when the API description cannot be loaded, and 5 when Hedra cannot be reached.

Stream commands exit with a code for each kind of failure, so a script can tell them apart. `hedra-cli sandbox <command> --help` prints the same table.

| Code | Meaning |
| --- | --- |
| 0 | Success. `exec`, `shell` and `cp` exit with the command's own code instead |
| 1 | Hedra returned an error |
| 2 | Not signed in, or the key was refused |
| 3 | Usage error: a flag or argument the command does not accept, or a missing one |
| 10 | The key lacks a sandbox scope |
| 11 | No such sandbox |
| 12 | Sandboxes are not enabled for this workspace |
| 13 | The sandbox is not ready, or it stopped |
| 14 | No GPU of that model is free |
| 15 | The wallet cannot pay |
| 16 | A limit was reached |
| 17 | Hedra or the network is unavailable; retry |
| 18 | The connection to the sandbox was lost |
| 19 | The request was refused, for instance a bad argument or a taken name |
| 129 | Hangup: the terminal closed, or SIGHUP |
| 130 | Interrupted with Ctrl-C |
| 141 | The output was closed, for instance by `head` |
| 143 | Terminated: SIGTERM, or Ctrl-Break on Windows |
| 255 | The output could not be written, or hedra-cli crashed; and for `exec`, `shell` and `cp`, any failure of hedra-cli's own |

Each failure prints one line on stderr that starts `hedra-cli: <class> (<code>):` and names the next step, such as:

```text
hedra-cli: Not found (11): No sandbox `train`. Run `hedra-cli sandbox ls`.
```

With an explicit `--format json`, the line is a JSON object instead, `{"error": {...}}`, whose `error` holds `class`, `exit_code`, `message`, `reason` and `trace_id`.

How each stream command uses the table:

| Command | Exit codes |
| --- | --- |
| `exec`, `shell`, `cp` | The command's own code, or for `cp`, the code of `tar` in the sandbox. Every failure of hedra-cli's own is 255, since the command can exit with any of 0 to 255; the `hedra-cli: <class> (<code>):` line says which failure it was. The exceptions are 3 for a usage error, 130 for Ctrl-C (under `-t` and in `shell`, only before the terminal is in raw mode; after that, Ctrl-C goes to the remote command), 141, 129 and 143. |
| `shell --gpu` | As `shell`. It also exits 255 whenever the sandbox it created may still be running, for instance when the stop could not be confirmed or a second Ctrl-C abandoned the create, and prints the sandbox's name and the command that stops it. |
| `logs` | 0 once the output is printed, including when there is none yet. 130 on Ctrl-C. Otherwise the code for the failure: 1, 2, 10, 11, 12, 13, 16, 17, 18 or 19, or 129, 141, 143 or 255. |
| `logs -f`, `attach` | As `logs`, except that Ctrl-C, which is how a follow ends, exits 0, and a dropped connection reconnects instead of exiting. A sandbox still starting after 15 minutes exits 13. |
| `port-forward` | Ctrl-C, which is how a forward ends, exits 0. 19 for a bad port or a local port it cannot listen on. Before the forward starts, the code for the failure, such as 2, 11 or 17. While it runs, it stops only when no later connection could succeed, with a code such as 13 (the sandbox stopped), 10 (the key lost its scope) or 2 (the key was revoked). 129 and 143 for signals. |
