Access almost all of the world's leading image, video, and audio models — including Nano Banana Pro, Veo, Grok, Kling, and more — via the Hedra API, using the same account your team uses to create content on the Hedra platform.

### Step 1: Use a paid Hedra account

The public API requires a paid Hedra subscription and uses the same Studio
credit balance as the Hedra app.

### Step 2: Register an API key

Go to [API keys](https://www.hedra.com/develop/api-keys) and generate a key. Make
sure the account has enough Studio credits for the generation you want to run.

### Step 3: Make your first API call

Set your API key and list available models:

```bash
export HEDRA_API_KEY="your_api_key"

curl https://api.hedra.com/web-app/public/models \
  -H "X-API-Key: $HEDRA_API_KEY"
```

### Step 4: Read a model's constraints and defaults

Each model in the response advertises the exact bounds it enforces and the
value it substitutes for any dispatch-shaping field you omit. Read this before
you submit so you know what a request will render — and be billed for — without
trial-and-error.

**Media-input constraints.** Every media-input field (start frame, source
video, audio reference, and so on) publishes the limits the API already
enforces:

- `max_file_size_bytes` — the byte cap for that slot. The platform caps images
  at 30 MB, audio at 100 MiB, and video at 500 MiB by default; individual model
  slots tighten this further (for example, Veo 3.1 caps input frames at 20 MB).
- `min_dimension_px` / `max_dimension_px` — pixel floors and ceilings for
  images and video frames (for example, Happy Horse requires 300×300 or above).
- `min_duration_ms` / `max_duration_ms` — per-file duration windows for video
  inputs.
- `max_total_duration_ms` — the combined-duration ceiling for a multi-file
  audio slot (for example, Seedance 2.0 accepts up to 15 seconds of audio
  reference across all files).

A key only appears when something actually checks it, so a missing bound means
that dimension is unconstrained for that model. These bounds now apply
uniformly whether you attach media by URL upload or by `{"source": "asset"}`
reference — an asset whose stored dimensions or duration are outside the
declared window is rejected before dispatch.

**Prompt length.** Text-prompt fields publish `minLength` and `maxLength` for
the 76 models whose provider documents a limit — for example, ElevenLabs v3
caps at 5,000 characters, Flash v2.5 at 40,000, Veo 3 at 20,000, GPT Image at
32,000. Validating prompt length client-side saves a mid-generation rejection
and, for text-to-speech, avoids being billed per character for a request the
provider will refuse. Prompt fields also publish `"pattern": "\\S"` — a
whitespace-only prompt is rejected at validation on every model that accepts
one, rather than 400ing at dispatch.

**Sizing requiredness and dispatch defaults.** `resolution`, `aspect_ratio`,
and `duration_ms` are classified per model from what the model actually offers:

- **Menu of two or more values** — the field is `required`. Omitting it is a
  field-level validation error rather than a silent substitution to a value
  you did not pick. A prompt-only submit to Seedream 4.0, for example, no
  longer renders a 2160×2160 square without you naming a size.
- **Menu of exactly one value** — the field stays optional and the single
  value is still published, so a schema-driven client can pick it up. Veo 2
  renders 5 seconds and only 5 seconds; you are not forced to restate its
  `duration_ms`.
- **Derived from an input you already supplied** — audio-driven avatar
  models take their length from the driving audio; video extensions take
  it from the source clip. The field is not required and no default is
  published.
- **Absent** — models that never accept a menu do not publish the knob at
  all. HiDream-O1 edit variants, for example, omit `resolution` because
  their provider picks the magnitude from the reference image; a field you
  cannot read on the wire cannot be billed for a value you never received.

Where a field does publish a JSON Schema `default`, that is the exact value
the request will render and be billed at when the field is absent — for
example, `hedra-avatar` and `hedra-character-3` publish `"default": "720p"`
for `resolution`, and veed-fabric-10 publishes `"default": "720p"`.

**Mode-dependent menus and forbidden fields.** Some models expose several
modes behind a discriminator (for example, `quality: standard` versus
`quality: pro` on Minimax Hailuo, or a text mode versus an image mode on
Flux Kontext Max) and each mode accepts a different subset of the top-level
menu. The schema publishes an `anyOf` of branches, one per mode, and each
branch carries the full contract for its mode:

- `required` lists the fields the mode demands.
- `properties.<field>.enum` narrows the top-level enum to the values the
  mode accepts. Kling-o3 at `quality: standard`, for example, publishes
  `resolution: ["720p"]` on its branch while `quality: pro` publishes
  `["1080p", "4K"]` — two of the three values in the merged menu are
  invalid whatever tier you pick.
- `properties.<field>: false` marks a field the mode rejects outright.
  Flux Kontext Max's image mode publishes `"aspect_ratio": false`, so
  passing `aspect_ratio` alongside `images` fails validation instead of
  400ing at dispatch.

Match your intended mode to one `anyOf` branch and submit the fields it
lists.

**Guidance strings.** Fields that need a plain-English note beyond the type
publish it under a `guidance` key alongside `description`. For example, on
`hedra-avatar` and `hedra-character-3` the `duration_ms` field explains that
the value trims or pads the driving audio and is billed accordingly. Read
`guidance` when building a schema-driven form or explaining a field to end
users.
